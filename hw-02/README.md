# ДЗ 2 — Plan-and-Execute агент на LangGraph

**Автор:** Моісеєнко Світлана · курс «Проєктування автономних агентів» (теми 3–4)

Агент з архітектурою **Plan-and-Execute**: planner складає повний план заздалегідь, executor
виконує його крок за кроком, replanner після кожного кроку вирішує `continue / revise / finish`.
Додатково реалізовано три production-можливості: **persistence** (`SqliteSaver`, файл, відновлення
за `thread_id`), **agentic RAG** (ChromaDB, 10 документів, інструмент `search_knowledge`) та
**human-in-the-loop** (`interrupt()` перед ризиковим інструментом + approve/reject).

## Архітектура

```
START → [planner] → [executor] → [replanner] ──continue/revise──┐
             │           ▲                                      │
             │           └──────────────────────────────────────┘
             │           │
             │       interrupt() перед ризиковим tool (book_hotel)
             │       → людина: approve / reject → Command(resume=...)
             │
             └ Plan (structured output)          [replanner] ──finish──→ END
```

* **`planner`** — генерує план через structured output `Plan(steps: list[str])`; промпт явно
  вимагає брати доменні факти з бази знань (`search_knowledge`), але не додавати зайвих кроків.
* **`executor`** — виконує ОДИН крок плану за ітерацію: один tool call або текстовий підсумок.
  Перед інструментом зі списку `RISKY_TOOLS` викликає `interrupt()` — стан зберігається у
  checkpointer, граф чекає на `Command(resume={"approved": ..., "comment": ...})`.
* **`replanner`** — structured output `ReplanDecision(action, steps, response, reason)`:
  `continue` (план актуальний), `revise` (замінити залишок плану), `finish` (фінальна відповідь).
  Conditional edge: `replanner → executor` або `replanner → END`.

**Стан (`PlanExecState`):** `input`, `plan` (залишок кроків), `past_steps` (з `operator.add`),
`decisions` (журнал рішень replanner-а), `response`.

**Guardrails:** `max_plan_steps` (обрізання плану), `max_total_steps` (зупинка нескінченного
replanning з поясненням у відповіді).

## Ключова відмінність від ДЗ 1 (ReAct)

| | ReAct (ДЗ 1) | Plan-and-Execute (ДЗ 2) |
|---|---|---|
| Рішення про наступний крок | «на льоту», після кожного observation | повний план заздалегідь |
| Структура графа | цикл `agent → tools → agent` | `planner → executor → replanner` |
| Корекція курсу | неявна, у наступному thought | явне рішення `continue / revise / finish` |
| Сильна сторона | короткі задачі, швидка реакція | послідовності з 3+ залежних дій |

## Production-можливості

### 1. Persistence — `SqliteSaver` (Секція 8)
Checkpointer працює поверх **файлу** `checkpoints.sqlite` (не `:memory:`). Демонстрація «збою»:
граф з `interrupt_before=["executor"]` виконує планування + перший крок, після чого з'єднання з БД
закривається, а об'єкти графа знищуються. «Новий процес» відкриває той самий файл, збирає граф
заново і за тим самим `thread_id` бачить увесь прогрес (виконані кроки, залишок плану, наступний
вузол) та доводить план до кінця. Наприкінці секції — вміст таблиці `checkpoints` по thread-ах.

### 2. Agentic RAG — ChromaDB (Секції 2, 6)
База знань «Подорожі Україною»: 10 документів (міста, бюджетування, політика бронювання,
транспорт, безпека). Ембеддинг — власний `HashingEmbedding` (хешування слів і символьних 3-грам):
детермінований, працює без мережі, покриває українську морфологію («Львів» ↔ «Львові»);
у production замінюється на нейронні ембеддинги без зміни коду інструмента.
Демонстрація агентності: питання про Карпати → планувальник сам додає крок `search_knowledge`;
чиста арифметика → план складається лише з `calculator`, RAG не викликається.

### 3. Human-in-the-Loop — `interrupt()` (Секція 9)
`book_hotel` позначено ризиковим (фінансове зобов'язання). Executor зупиняє граф через
`interrupt()` з деталями дії (інструмент, аргументи, крок плану). Обидва сценарії показані
на окремих thread-ах:
* **approve** → інструмент виконується, результат позначено «ПІДТВЕРДЖЕНО людиною», план завершується;
* **reject** → інструмент НЕ виконується, replanner ухвалює `finish` з поясненням
  «людина відхилила ризикову дію».

Оскільки interrupt зберігається у checkpointer, очікування на рішення людини переживає
перезапуск процесу.

## Інструменти

| Інструмент | Призначення | Валідація (`field_validator`) |
|---|---|---|
| `search_knowledge` | RAG-пошук у ChromaDB | запит ≥ 3 символів, `top_k` 1–5 |
| `calculator` | арифметика | лише цифри й оператори, безпечний AST |
| `convert_currency` | конвертація валют | сума > 0, коди валют по довіднику |
| `get_weather` | погода по місту | місто нормалізується і перевіряється по довіднику |
| `book_hotel` | **ризиковий**: бронювання готелю | готель по довіднику, ночі 1–30; виконується лише після approve |

## LLM-провайдер

* **Основний:** OpenAI `gpt-4.1` через `ChatOpenAI` — активується автоматично за наявності `OPENAI_API_KEY`.
* **Фолбек:** `ScriptedPlanExecLLM` — власна реалізація `BaseChatModel`, що емулює всі три ролі
  за схемою прив'язаних інструментів: `bind_tools([Plan])` → планувальник, `bind_tools([ReplanDecision])`
  → replanner, `bind_tools(TOOLS)` → виконавець. Ноутбук повністю відтворюється без ключа, а
  демонстрації replanning/HITL/persistence — детерміновані.

## Аналіз

* **План як контракт.** План видно до виконання — його можна показати людині, залогувати й
  порівняти з фактичною траєкторією. Сценарій «поїздка до Львова» — 5 залежних кроків
  (база знань → погода → валюта → бюджет → бронювання): planner фіксує послідовність одразу,
  executor не «губить» мету посередині.
* **Replanning — головний запобіжник.** У демо «Львів vs Париж» інструмент погоди падає на
  валідації (`Париж` відсутній у довіднику). Замість краху всього плану replanner ухвалює
  `revise`: підставляє запасне місто і зберігає решту кроків. Важлива деталь: рішення ухвалюється
  за результатом **останнього** кроку, інакше згадка про стару помилку в підсумках провокує
  повторний replan (це реальний баг, спійманий під час розробки).
* **Ціна архітектури.** Кожен крок — щонайменше два LLM-виклики (executor + replanner) плюс
  планування. Для «порахуй 15% від 2400» це надлишково — ReAct з ДЗ 1 ефективніший; перевага
  Plan-and-Execute проявляється від ~3 залежних кроків.
* **Persistence змінює модель відмов.** «Збій» коштує нуль втраченого прогресу: стан на кожному
  кроці вже у SQLite, а відновлення — це просто повторний `invoke` з тим самим `thread_id`.
  Той самий механізм безкоштовно дає HITL-очікування будь-якої тривалості.

## Обмеження й наступні кроки

* Офлайн-фолбек скриптований: реальна варіативність планів з'являється лише з живим LLM.
* `HashingEmbedding` — лексичний (збіг слів/грам), без справжньої семантики; для production —
  нейронні ембеддинги та персистентний ChromaDB (`PersistentClient`).
* Replanner викликається після кожного кроку — для довгих планів раціональніше перевіряти план
  лише після помилок або кожні N кроків.
* Approve/reject подається програмно через `Command(resume=...)`; у застосунку це той самий API,
  але за UI-формою підтвердження.
