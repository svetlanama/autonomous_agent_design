# ДЗ 1 — ReAct-агент на LangGraph

**Автор:** Моісеєнко Світлана · курс «Проєктування автономних агентів» (теми 1–2, 4)

ReAct-агент (Reasoning + Acting) на LangGraph: цикл `LLM → tools → LLM`, чотири інструменти
з Pydantic v2 валідацією, structured outputs, захисні механізми (`max_steps`, `timeout`,
детекція зациклення) та повне логування траєкторії у JSON.

## Архітектура

```
            ┌──────────────────────────────────────────┐
            ▼                                          │
START → [agent] ──tool_calls?──yes──→ [tools] ──── не зупинено
            │                             │
            └── ні / зупинено ─→ [finalize] ←── зупинено
                                    │
                                    ▼
                                   END
```

* **`agent`** — перевіряє guardrails, викликає LLM з прив'язаними інструментами (`bind_tools`).
* **`tools`** — виконує tool calls, перехоплює помилки валідації та повертає їх як `Observation`,
  шукає повторні виклики.
* **`finalize`** — формує structured output `FinalAnswer(answer, tools_used, confidence)`
  через `with_structured_output`.
* **Conditional edges:** `agent → tools | finalize`, `tools → agent | finalize`.

**Стан (`AgentState`):** `messages` (з `add_messages`), `step`, `started_at`, `seen_calls`,
`halted`, `halt_reason`, `trajectory` (з `operator.add`), `final`.

## Інструменти

| Інструмент | Призначення | Валідація (`field_validator`) |
|---|---|---|
| `calculator` | арифметичні обчислення | лише цифри й оператори, ≤ 200 символів, безпечний AST замість голого `eval` |
| `convert_currency` | конвертація валют за фіксованим курсом | сума > 0 та ≤ 1e9, код валюти нормалізується й перевіряється по довіднику |
| `get_weather` | погода по місту | назва міста нормалізується (`  київ ` → `Київ`) і перевіряється по довіднику |
| `analyze_text` | статистика тексту | текст 10–5000 символів, `top_n` у межах 1–10 |

## LLM-провайдер

* **Основний:** OpenAI `gpt-4.1` через `ChatOpenAI` — активується автоматично за наявності `OPENAI_API_KEY`.
* **Фолбек:** `ScriptedToolCallingLLM` — власна реалізація `BaseChatModel` з підтримкою `bind_tools`
  (а отже й `with_structured_output`), що емулює tool calling за скриптованим планом.
  Потрібна, щоб ноутбук повністю відтворювався без ключа й без мережі, а демонстрації guardrails
  були детермінованими, а не залежали від поведінки моделі.

## Захисні механізми

| Механізм | Реалізація | Демонстрація |
|---|---|---|
| `max_steps` | лічильник `step` у стані, перевірка на вході у вузол `agent` | план на 8 кроків при ліміті 3 → зупинка на 3-й ітерації |
| `timeout` | `started_at` у стані, перевірка `elapsed > timeout_s` між кроками | затримка LLM 0.1 с при тайм-ауті 0.15 с → зупинка на 2-й ітерації |
| детекція зациклення | підпис `name(args)` у `seen_calls`, повторний виклик зупиняє цикл | модель повторює `get_weather({"city": "Львів"})` → зупинка |

У всіх випадках агент не падає з винятком, а коректно доходить до `finalize` і повертає
`FinalAnswer` з `confidence = 0.0` та причиною зупинки в полі `answer`.

## Аналіз

* **Цикл працює як ReAct.** У простому кейсі (TC1) агент робить один хід «міркування → дія →
  спостереження» і завершується structured output. У TC2 модель викликає два незалежних
  інструменти **в одному ході** — це економить цілу ітерацію порівняно з послідовними викликами.
* **Валідація — частина міркування агента.** У TC4 перший виклик падає на `field_validator`
  (`amount <= 0`, невідома валюта `XYZ`), помилка повертається в діалог як `Observation`, і на
  наступному кроці агент виправляє аргументи. Тобто валідація не ламає цикл, а дає моделі
  зрозумілий зворотний зв'язок — саме тому в `raise ValueError` варто писати людський текст
  зі списком допустимих значень.
* **Guardrails спрацьовують раніше за `recursion_limit` LangGraph** і дають осмислену причину
  зупинки замість технічного винятку.
* **Вартість кроку.** Найдорожчий ресурс — LLM-виклики, а не інструменти: на офлайн-провайдері
  уся сюїта виконується за мілісекунди. Реальний час роботи агента визначається кількістю
  ітерацій, тому скорочення кроків (паралельні tool calls, точні описи інструментів) впливає
  на латентність і ціну сильніше за оптимізацію самих інструментів.

## Обмеження й наступні кроки

* Тайм-аут перевіряється **між кроками**, тож один аномально довгий tool call його не перерве —
  для продакшену потрібен тайм-аут на рівні окремого виклику інструмента.
* Детекція зациклення точна (повний збіг аргументів): `Київ` / `київ ` нормалізуються валідатором,
  але семантично однакові `2+2` і `2 + 2` вона не зловить.
* Немає персистентності — додавання `checkpointer` дало б продовження діалогу та human-in-the-loop.
